# 🏆 Конкурсы, программы и гранты ТПУ

Веб-приложение для единого каталога конкурсов, программ, грантов и стипендий ТПУ. Система включает проектирование базы данных с нуля, административную панель для внесения данных, а также публичный интерфейс с поиском, фильтрацией и календарным представлением.

Консультант: Куртенков Денис Геннадьевич (denis@tpu.ru).

## Предпосылки

Информация о конкурсах, программах и грантах ТПУ не систематизирована: часть данных хранится в 1С, часть — в разрозненных документах. Студенты и сотрудники не имеют единого удобного инструмента для поиска актуальных возможностей. Отсутствие структурированной базы данных затрудняет оперативное обновление и публикацию информации. Проект решает задачу создания полноценного каталога с нуля — от архитектуры БД до публичного интерфейса.

## Цели проекта

1. Спроектировать реляционную базу данных для хранения конкурсов, программ, грантов и стипендий
2. Разработать REST API для работы с каталогом
3. Реализовать административную панель для внесения и управления данными
4. Создать публичный веб-интерфейс с каталогом, поиском и фильтрацией
5. Обеспечить календарное и списочное представление с разделами «Идёт регистрация» и «Ближайшая регистрация»

## Быстрый старт

### Требования

- Node.js >= 18
- npm или yarn
- PostgreSQL >= 15
- Docker (опционально)

### Установка и запуск

```bash
# Клонирование репозитория
git clone <url-репозитория>
cd <имя-проекта>

# Установка зависимостей
npm install

# Настройка переменных окружения
cp .env.example .env
# Отредактируйте .env — укажите параметры подключения к БД

# Запуск миграций БД
npm run db:migrate

# Запуск в режиме разработки
npm run dev
```

## Как мы работаем с Git

### Основные правила

Мы используем **Git Flow** — модель ветвления, которая помогает организовать совместную разработку и не ломать рабочий код.

### Ветки

| Ветка | Назначение |
|-------|-----------|
| `main` | Стабильная версия. Сюда попадает только проверенный и протестированный код. Напрямую в `main` **никто не коммитит** |
| `develop` | Основная ветка разработки. Сюда вливаются все завершённые задачи. Из неё собираются релизы в `main` |
| `feature/*` | Ветки под конкретные задачи. Создаются от `develop`, вливаются обратно в `develop` через Pull Request |
| `fix/*` | Ветки для исправления багов. Аналогично `feature/*` |

### Как работать с задачей

```
1. Берёшь задачу на доске YouGile → переводишь в «В работе»

2. Создаёшь ветку от develop:
   git checkout develop
   git pull origin develop
   git checkout -b feature/название-задачи

3. Работаешь в своей ветке, делаешь коммиты:
   git add .
   git commit -m "feat: добавлена модель конкурса в БД"

4. Когда задача готова — пушишь ветку и создаёшь Pull Request:
   git push origin feature/название-задачи
   → Создаёшь PR из feature/название-задачи в develop

5. PR проходит код-ревью от лида (куратора) → после одобрения вливается в develop

6. Переводишь задачу на доске в «Готово»
```

### Правила именования веток

```
feature/grants-api          — новая функциональность
feature/admin-panel         — новая функциональность
fix/category-filter-bug     — исправление бага
refactor/database-schema    — рефакторинг без изменения поведения
docs/api-endpoints          — документация
```

### Правила коммитов

Используем [Conventional Commits](https://www.conventionalcommits.org/ru/) — это упрощает чтение истории и автоматизацию:

```
feat: добавлена миграция для таблицы конкурсов
feat: реализован CRUD API для грантов
fix: исправлена валидация дат регистрации
docs: описана ER-диаграмма БД
style: форматирование кода модуля grants
refactor: вынесена общая логика фильтрации
test: добавлены тесты для API конкурсов
chore: обновлены зависимости NestJS
```

**Формат:** `тип: краткое описание на русском`

### Правила Pull Request

1. **Название PR** — кратко описывает что сделано (например: `feat: CRUD API для грантов`)
2. **Описание** — что сделано, как проверить, скриншоты (если есть UI)
3. **Один PR = одна задача** — не смешивайте несколько задач в одном PR
4. **PR ревьюит лид (куратор)** — без одобрения не мёржим
5. **Конфликты** — автор PR разрешает конфликты самостоятельно, при необходимости обращаясь за помощью

### Чего делать нельзя

- ❌ Коммитить напрямую в `main` или `develop`
- ❌ Делать `force push` в общие ветки
- ❌ Мёржить свой PR без ревью
- ❌ Оставлять ветку без PR дольше 3 дней
- ❌ Коммитить сгенерированные файлы (`node_modules/`, `dist/`, `.env`)
